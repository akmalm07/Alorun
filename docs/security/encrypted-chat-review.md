# Encrypted chat security review

Status: implementation review and synthetic tests by the implementation author; **not independent security approval**. Do not deploy as production or use for sensitive data until the release blockers below are resolved and reviewed independently.

## Scope and design

The client authenticates with Supabase and verifies that the chat URL uses HTTPS. It creates a random account data key and wraps it with a key derived from a separate passphrase using a random salt and scrypt. The server stores the wrapped key and per-thread XChaCha20-Poly1305 ciphertext keyed by the verified Supabase user ID. Authenticated associated data binds a record to its account, type and ID. A new device signs into the same account and uses the passphrase to unwrap the same data key. The key is kept in app memory only. User messages and AI replies are encrypted before storage; AI calls temporarily transmit bounded plaintext to the server and the selected OpenAI or Anthropic provider. Provider retention policies apply.

The Supabase PostgreSQL store and app are a development implementation. The legacy plaintext database remains on disk as an explicit migration source. The import reads it locally, encrypts on that computer, imports under the authenticated account, verifies each copy, refuses differing existing records, and preserves the original. Account IDs, record IDs, ciphertext sizes, versions, and request metadata remain visible.

## Review findings and required follow-up

- **Release blocker — no independent review or device validation.** The cryptographic construction, libraries, Expo/Hermes random source and text encoding, TLS proxy, and identity configuration require independent security review and real Android testing, including the 128 MiB scrypt cost on lower-end devices. `text-encoding` is an unmaintained compatibility dependency and must be evaluated or replaced before release.
- **Release blocker — incomplete lifecycle and operational controls.** There is no account deletion, encrypted export, password/passphrase change, user-managed device revocation, key rotation, account recovery or server backup/restore workflow. A lost passphrase prevents recovery. The Supabase integration and deployment still need staging validation and operational review. It has no durable per-user AI spending quota; the in-memory rate limit is not a production abuse control.
- **Release blocker — unverified transport and deployment.** The server itself speaks HTTP and relies on Cloud Run HTTPS termination or a correctly configured reverse proxy; the client rejects non-HTTPS API URLs, but no proxy configuration or deployment is included. Protection of server files, backups, logs, proxy logs, and infrastructure against compromise remains to be verified. The old plaintext development database and backups must be separately handled by the user.
- **Integrity limitation — replay and deletion.** AEAD detects modification and account/record substitution, and revision checks prevent ordinary stale writes. A malicious or compromised server can still replay older valid ciphertext, remove records, replace the wrapped vault, or deny access; there is no trusted rollback protection or availability guarantee.
- **Processing boundary.** The application server and AI provider see the current conversation context in plaintext for an AI request. A compromised server or modified client can capture it, and the service cannot guarantee provider-side retention or deletion. Metadata remains visible. Do not describe this as end-to-end secrecy from the AI service.
- **Memory and session handling.** JavaScript cannot reliably erase all copies of secrets; the passphrase and data key may remain in runtime memory. Unlocked keys are not persisted in platform key storage, and sign-in must be repeated after session expiry. Background lock, compromised-device protection, crash-dump behavior and screenshots need review.
- **Authentication integration.** Unit tests mock token verification; real Supabase sign-in, token expiry, user provisioning, revocation and cross-tenant isolation against an actual deployment have not been exercised. The server authenticates each request using the provider's `getUser` endpoint and does not accept a client-supplied owner ID.

## Evidence

The automated tests create fictional legacy conversations, import and verify them, reopen the same wrapped key as a second simulated device, and confirm the original data remains. API tests use mocked identities to check account separation, stale revision rejection, no access to the legacy API, and absence of synthetic plaintext in the test SQLite store. The PostgreSQL migration is also checked against a disposable PostgreSQL instance with simulated Supabase roles; a live Supabase project has not been tested. Cryptographic tests attempt wrong keys and passphrases, modification of ciphertext, salts and nonces, and cross-account/type/record substitution. These tests are not a penetration test and cannot prove complete security. No real account, production data, or infrastructure was attacked.
